# LINEチャネルアクセストークン キャッシュ最適化

**実装日**: 2025-10-19  
**Worker Version**: `1798c286-6eba-4daf-88cf-b1041aa08b77`

## 背景

### 問題点
当初の実装では、サービスメッセージを送信するたびにLINE APIから新しいチャネルアクセストークンを発行していました。

```typescript
// 問題: ユーザーが応募するたびにLINE APIにリクエスト
ユーザーA応募 → LINE APIリクエスト → トークン発行 (1回目)
ユーザーB応募 → LINE APIリクエスト → トークン発行 (2回目)
ユーザーC応募 → LINE APIリクエスト → トークン発行 (3回目)
...
30回目 → LINE APIの発行制限に達してエラー
```

**課題**:
- 不要なLINE APIリクエスト（発行したトークンは30日間有効なのに毎回発行）
- レスポンス遅延（ネットワーク往復で~500ms）
- 30件の発行制限に達する可能性

## 重要な発見

### チャネルアクセストークンは全ユーザーで共有

ユーザーが「このトークンってユーザーは関係なくってこっち側の話ってこと？」と質問してくれたことで、以下が明確になりました：

**トークンの種類**:

1. **チャネルアクセストークン** ← 今回の最適化対象
   - 用途: アプリ（チャネル）の認証
   - スコープ: アプリ全体で1つ
   - 所有者: サービス運営者
   - 共有: **全ユーザーで共有可能** ✅

2. **LIFFアクセストークン** ← ユーザー個別
   - 用途: 個別ユーザーの認証
   - スコープ: ユーザーごとに異なる
   - 所有者: 各ユーザー
   - 共有: 不可 ❌

この理解により、チャネルアクセストークンをメモリにキャッシュして全ユーザーで再利用できることが判明しました。

## 解決策: メモリキャッシュ

### 実装内容

```typescript
/**
 * チャネルアクセストークンのキャッシュ
 * 
 * チャネルアクセストークンは全ユーザーで共有されるアプリ認証用トークンなので、
 * メモリにキャッシュして再利用することでパフォーマンスを向上させます。
 */
let cachedChannelAccessToken: {
  token: string
  expiresAt: number
} | null = null

async function getChannelAccessToken(env: Bindings): Promise<string> {
  const now = Date.now()
  
  // キャッシュが有効期限内なら再利用
  if (cachedChannelAccessToken && cachedChannelAccessToken.expiresAt > now) {
    console.log('[LINE] Using cached channel access token')
    return cachedChannelAccessToken.token
  }
  
  // キャッシュがない、または期限切れなら新規発行
  const response = await fetch('https://api.line.me/v2/oauth/accessToken', {
    method: 'POST',
    // ...
  })
  
  const data = await response.json()
  
  // キャッシュに保存（29日間）
  cachedChannelAccessToken = {
    token: data.access_token,
    expiresAt: now + (29 * 24 * 60 * 60 * 1000)  // 29日後
  }
  
  return data.access_token
}
```

### 動作フロー

```
初回リクエスト:
  ユーザーA応募 → LINE APIリクエスト → トークン発行 → キャッシュに保存
  
2回目以降（29日以内）:
  ユーザーB応募 → キャッシュから取得 (LINE APIリクエストなし)
  ユーザーC応募 → キャッシュから取得 (LINE APIリクエストなし)
  ユーザーD応募 → キャッシュから取得 (LINE APIリクエストなし)
  ...
  
29日後:
  ユーザーZ応募 → キャッシュ期限切れ → LINE APIリクエスト → 新しいトークン発行
```

### キャッシュの有効期間

- **トークンの実際の有効期間**: 30日
- **キャッシュの有効期間**: 29日
- **理由**: 1日の安全マージンを確保

## Cloudflare Workersの特性

### メモリキャッシュの永続性

Cloudflare Workersはステートレスですが、メモリキャッシュは一定時間保持されます：

```
Worker起動 → リクエスト処理 → メモリにキャッシュ保持
    ↓
同じWorkerインスタンスで処理されれば、キャッシュが使える
    ↓
Workerが停止/再起動されると、キャッシュは失われる
    ↓
再起動後は自動的に再発行される（問題なし）
```

**現実的なシナリオ**:
- **アクセスが頻繁**: Workerが起動し続け、キャッシュが有効に機能
- **アクセスが少ない**: Workerが停止し、キャッシュが失われる
  - でも、次回アクセス時に自動的に再発行されるので問題なし

### キャッシュ失効時の動作

```
1. Worker再起動（キャッシュ失効）
   ↓
2. ユーザーが応募
   ↓
3. cachedChannelAccessToken === null
   ↓
4. LINE APIから新しいトークン発行
   ↓
5. キャッシュに保存
   ↓
6. 以降29日間は再利用
```

**影響**: なし（自動的に回復）

## 安全性

### 1. トークンの有効性

- トークン自体は30日間有効
- キャッシュは29日で期限切れ
- 1日の安全マージンを確保

### 2. Worker再起動時

- キャッシュは失われる
- 自動的に再発行される
- エラーは発生しない

### 3. 複数Workerインスタンス

Cloudflare Workersは複数のインスタンスが起動する可能性がありますが：

- 各インスタンスが独自のキャッシュを持つ
- 最大でも数個のトークンが発行されるだけ
- 30件の制限には全く影響しない

### 4. セキュリティ

- トークンはメモリにのみ保持
- 外部に漏洩しない
- ログに出力されない

## LINE APIガイドラインへの準拠

LINE公式ドキュメントより：

> 短期のチャネルアクセストークンについては、チャネルを使用するたびにチャネルアクセストークンを再発行しないでください。
> 短時間に大量のチャネルアクセストークンを発行し、LINEプラットフォームの動作に影響を与えると判断された場合、発行を一時的に制限する場合があります。
